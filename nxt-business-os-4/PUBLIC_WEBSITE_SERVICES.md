# Public website service flows

The `/domains` page shows confirmed Available / Unavailable results and adds selected names to the customer checkout. Customers supply owner, billing and business details; NXT handles technical contacts, nameservers and registry submission behind the scenes. The two-to-three-hour estimate begins after complete details and payment.

`POST /api/public/domain-registration` validates on the server and rechecks `.co.zw` availability. With `RESEND_API_KEY` and `NOTIFICATION_FROM` set, it sends one email to the fixed address `dns@nxt-workforce.com`, with the full domain as subject and one ASCII `.txt` attachment. The supplied ZISPA 3.3 template retains its labels and line layout. The Resend transport encodes attachments for delivery to NXT's inbox; the decoded file is ASCII with CRLF line endings. NXT must verify the required signed owner documents, payment and authoritative DNS, then submit from its registered registrar mailbox. This endpoint does not email ZISPA or purchase domains.

The legacy registration API remains available for existing integrations. Without email configuration it returns the prepared application for download. The new cart checkout stores orders and does not invoke this legacy submission endpoint. Paid-order registration fulfilment and ZISPA submission are still manual staff tasks. Set the two server-only email variables on the website Vercel project to enable automatic delivery. Sensitive keys on a different project cannot be read/copied through the connector. Do not place keys in the frontend or this archive.

Normal 123 Reg accounts have no verified API connection here. International applications can be fulfilled manually in the NXT 123 Reg account. Inconclusive online availability checks show a retry message; they are never converted to false Unavailable results. A registrar API with suitable supported extensions is needed for comprehensive automated international checks and purchases.

The floating WhatsApp action opens NXT's existing +263790050483 contact. Ask AI calls `/api/public/service-assistant`, which uses only the public catalogue in `src/lib/public-service-catalogue.ts`; it has no CRM access or action tools. Replies can suggest up to three known service links. Keep that catalogue in sync with the service pages.

AI requires `NXT_PUBLIC_AI_ENABLED=true` and Vercel deployment OIDC (or server-only `AI_GATEWAY_API_KEY` outside Vercel). The selected model is configurable in `NXT_PUBLIC_AI_MODEL`; `google/gemini-2.5-flash-lite` was verified in the live Gateway catalogue. Input/history and output tokens are bounded. Per-instance throttling is best effort, not a distributed spending cap; Gateway credit/budget settings remain the account-level limit. No credit purchase, auto-recharge or budget increase was configured. A gateway verification or credit block falls back to clearly labelled matches from the public service directory. These are fixed catalogue entries, not model-generated answers.

Photos in `public/v6/photos/` are the owner's supplied originals. The source filenames are recorded in `credits.json`. Spotly's supplied transparent SVG joins the animated client strip. The homepage's white animated-X hero remains unchanged.

Verification: focused server tests cover validation, cross-site requests, malformed/oversized input, ASCII formatting, fixed recipients, delivery failures, download fallback, safe catalogue links and throttling. Browser checks cover the wizard, retries, mobile layouts and chat. Live delivery requires an actual configured sender; a successful mock test does not prove mailbox delivery.

## Customer domain checkout (2026-11-01)

- `/domains` adds available domains to a cart. Only names are kept in browser storage; customer details, passwords and payment OTPs are not.
- `/domain-checkout` collects billing contact, optional separate registrant, core business, proposed use and legal notices address. Technical hosting and registry fields are handled by NXT.
- `/domain-account` supports email/password signup, email confirmation, sign-in/out and order history. Account cookies are Secure, HttpOnly, host-only and SameSite=Lax. Signup does not create staff memberships or grant CRM access. Existing verified Supabase accounts can sign in.
- Current fixed prices are **unset and disabled**. Set both `registration_cents` and `renewal_cents`, inclusive of applicable charges, in `nxt_domain_prices`, then enable only the extensions NXT can fulfil. Do not import Webdev's $5 price or VAT assumptions. The review can collect account signups but cannot submit/pay an unpriced order.
- The database calculates the total from its own price catalogue and snapshots one-year registration/renewal prices. The browser cannot choose amounts, currency, owner IDs, payment status or fulfilment status. Separate authenticated customers cannot view each other's orders.
- Apply `20261101164010_domain_customer_checkout.sql` once to a new environment; it is already applied to the existing NXT Supabase project. Customer data is in `nxt_domain_orders`; Omari sessions are service-role-only in `nxt_domain_payments`.
- Public checkout uses the existing Supabase URL and publishable key. Signup confirmation email uses the existing Supabase Auth configuration. A user must confirm the email before signing in; return to the domain account page after confirmation. End-to-end mailbox delivery requires a real customer test.
- Omari remains disabled. To activate after merchant approval and a successful test: configure **server-only** production `OMARI_API_KEY`, `OMARI_MODE=production`, `SUPABASE_SERVICE_ROLE_KEY`, then set `NXT_DOMAIN_PAYMENTS_ENABLED=true` on the website project. Existing private Business OS credentials were not copied, and no live charge was attempted. The Omari API origin is fixed to the supplied production v1.3.0 endpoint.
- Omari OTP initiation uses the stored order amount, rechecks domain availability and allocates one payment reference per order. Atomic state transitions permit only one debit request. Timeout/unknown results require query/reconciliation, never a blind retry. Only a successful provider query with matching reference, currency, amount and nonempty payment reference marks an order paid. OTPs are never stored. A paid order remains awaiting registration until registry confirmation.
- Failed/expired OTP or ambiguous provider sessions are left for staff reconciliation; do not delete payment records or create a second reference without checking Omari. The old private invoice payment flow is unchanged.
- The 123 Reg browser account still needs sign-in. A normal retail account has no confirmed registration API integration; no automated purchases or reseller entitlement are implied by this checkout.
